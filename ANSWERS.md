1. How would you promote an internal AI platform inside the company?

Adoption isn't won through communication, it's won by removing obstacles. I wouldn't start with announcements, but with 2-3 teams that have a real pain point, and deliver a visible result within two weeks — one demonstrated case is worth ten presentations. From there I'd rely on champions in each department, who translate the use case into their own team's language, because adoption spreads between peers, not top-down. The non-negotiable condition is that someone gets their first useful result in minutes, not days: sign-in with the company account, access they activate themselves without a ticket, compatibility with what technical teams already use, and ready-to-run examples. If the path to a first answer goes through three approvals, the user is already on ChatGPT.

I'd measure adoption through weekly active users, not accounts created, and through a Governed Ratio how much of the company's actual AI usage goes through the platform. The denominator isn't directly visible, so I'd estimate it from three sources: network telemetry (unique users and upload volume to external AI services), identity signals (AI apps people have granted SSO access to, subscriptions expensed individually, installed applications), and an anonymous survey asking directly about frequency and, more importantly, why not the internal platform. I'd report a range rather than an exact figure and track the trend — and the answers to that "why not" essentially write the roadmap for me.

2. HR asks you to build an agent that picks the best CV from a pool of candidates. Who do you talk to first, and why?

Legal department. Recruitment is explicitly classified as a high-risk AI system under the EU AI Act. This isn't an architecture discussion, it's the one that determines whether the project is allowed to exist in the form it was requested.

Right after that, I'd go back to HR to reframe the request: from a system that decides to a system that helps a human decide. "Pick the best CV" isn't something you can build responsibly; structured skill extraction, checking mandatory criteria, summarisation and ranking with explanations with the final decision always resting with a person is. I'd also build in a bias audit before any pilot (identical CVs with names, gender or university swapped), because a model discriminates indirectly through exactly those signals. The first question isn't "how do I build this", it's "are we allowed to build this the way it was asked for".

3. As an internal candidate, how would you improve our AI platform?

For the first 30 days I'd listen and measure rather than propose. From what I've seen, the technical side is already solid. That's not where the problem is. The real gap is between what the platform can do and what people know it can do: most use it as a simple chat, even though it has Knowledge Bases, assistants and memory across conversations. So my first priority wouldn't be architecture, it would be adoption — and I'd start by talking to the people who tried it and gave up, because they tell me exactly where the value is being lost.

Concretely, I'd work on three fronts. First, enablement in the format people actually consume: 30-second clips, one per feature, showing a real outcome rather than an interface tour nobody reads a 20-page wiki to find out what a Knowledge Base is. Second, ready-made Knowledge Bases per department, not left to each individual: if a team has to build its own context from scratch, it never will. Third, visibility into usage which models are being used, which assistants are actually active, where the budget goes because without that data you can't properly prioritise what comes next.

4. How would you reduce shadow AI in the company?

Shadow AI is a symptom, not a cause: people aren't careless, the official platform is too slow, too limited, or invisible. So I'd start by understanding why visibility through proxy and DNS logs plus an anonymous survey and only then make sure the internal platform actually does what the external tools do. Blocking without an alternative just moves the problem to personal phones, where you see nothing at all and the risk is highest.

Order matters: first make the internal platform the easiest path (good models, instant access, no tickets), then write a one-page policy with concrete examples of which data can go where, then offer a window where people can openly say what they're using and get help migrating, with no penalties otherwise you lose exactly the visibility you just gained. Technical controls come last and gradually: filters on data leaving the company, then selective blocking of only the highest-risk services. Success isn't "zero shadow AI", it's increasing the share of usage that flows through visible, controlled channels.

5. Describe how you would build a load balancer for Ollama.

The main constraint isn't traffic, it's that each node keeps the model loaded in GPU memory. If I distribute requests in turn without accounting for that, nodes end up constantly loading and unloading models — tens of seconds lost on every switch. So I route based on the model, not the request. A gateway (LiteLLM or a custom router) periodically asks each node which models it has available and which are currently loaded, then picks in this order: a node that already has the model loaded → among those, the least busy one → otherwise, the node with the most free memory. On top of that: I keep frequently used models permanently loaded, put a capped queue in front that politely rejects excess requests instead of overwhelming a node, check node health periodically and pull unresponsive ones out of the pool, and make sure responses reach the user as they're being generated. The metric I track is how long until the first word appears, not how long the full response takes.

I'd add one caveat though: for a small pool, LiteLLM with model groups covers most needs and I wouldn't write custom code. And if we're talking serious volume on shared GPUs, I'd question Ollama itself — there are alternatives built specifically for production (vLLM, TGI) that serve several times more users on the same hardware, because they batch requests intelligently. Ollama is excellent for developers and prototyping; in a production context with many users, the load balancer solves distribution, but not the efficiency of each individual node.
